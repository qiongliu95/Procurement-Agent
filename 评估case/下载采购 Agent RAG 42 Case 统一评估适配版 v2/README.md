# 采购 Agent RAG 42 Case ——统一评估适配版 v2

本包**升级了已有的42条 Case，而非新增或重新抽样题目**。分类：单条件10、复合条件10、跨文档10、证据不足6、路由6。保留原始题目、标准答案要点、原候选文档ID和禁止行为。

## 与目前框架的匹配边界

依据目前已知的采购 Agent 评估需求（Case → 真实Agent运行 → Trace/检索证据/最终状态 → Checker → 指标 → Bad Case），统一出 `cases_v2.jsonl` 主格式、`cases_v2.csv` 人工审核表和 `framework_mapping.json`。**无法访问Windows本地自动化评估Runner/Checker源码**，所以这些是待适配的可移植字段约定，**不是声称已兼容既有CLI或评估器输入模式**。不要仅通过改后缀直接喂给不兼容的Runner。

## 评估层级与边界

- `rag_retrieval`：相似度Top-K命中和目标证据覆盖，不评估生成。
- `rag_answer`：必要回答要点与引用支持；不可把文档命中当作回答正确。
- `cross_document_coverage`：跨文档指定多个必需文档，评估各必要维度是否有证据。
- `abstention`：没有证据时不编造；部分可回答时可说明未知。
- `agent_routing` / `task_safety`：RAG READ vs 结构化API、确认门禁、禁止无授权写入。
- **API-only案例不纳入RAG检索命中率分母**；知识咨询不可触发写入，修改Case RAG-042 在用户确认前必须停在确认门禁。
- **不设置未经确定的评分权重、最低相关度、Top-K大小或成功率阈值**。第一次评估输出分项指标及Bad Case，权重和门槛另行确定。

## 数据来源与待核对项

原始v1的42条Case来自现有V1–V4候选稿，现有本地副本为65篇**审校前版本**。用户本地52篇正式审校本及修改后manifest无法直接读取，所以`gold_validation.status`均待核对，并不表示52篇已验证覆盖。

Codex入库前必须：
1. 读取正式52篇manifest，验证候选文档是否有效、来源是否仍适用；修正排除掉的候选文档，**不可凭原65篇盲打分**。
2. 四篇文档的修订需要特别关注：KB-002、KB-003、KB-010、PKB-V4-048。
3. 对跨文档题把必要证据分为每个文档应证明的事实；有些旧版标准要点是合并句，务必细化并人工审核，不可因为引用3份文档就自动判PASS。
4. API-only和真实申请ID（如PR-001）需通过有效Fixture/数据库查到真实记录；无记录则允许明确报不存在，**不得伪造**。避免使用相互污染的写入状态运行Case。
5. 根据现有Runner和Trace字段实现薄适配，不修改Agent主流程；评分器只使用真实工具回执、检索片段、最终回答和业务状态。

## 导入前检查与运行

包内 `validate_package.py` 能核对Case数量、类别、ID唯一性、路由与写入约束一致性。执行：`python validate_package.py`。这不是Agent评分器，也不需要DeepSeek。

统一评估完成后应输出：每类有效Case数、未运行与无效样本数，检索命中、跨文档覆盖、回答要点/忠实性、拒答、路由、写入安全，以及固定Bad Case归因类别（检索/证据缺失/生成/路由/系统状态/评估集）。保留raw trace且不要用Judge结论替代原始证据。
